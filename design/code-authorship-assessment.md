# 代码来源评估：人工编写、AI 辅助还是混合？

评估日期：2026-10-04。当前提交：`83c178950627478356281fb2d4cc748487d1031a`。范围为本地可见 Git 历史、当前源码/生成脚本、开发指令及本次对话的已知产出；没有访问原作者私有开发记录。

## 结论

**无法仅凭当前仓库，可靠确定 ZCode 产品代码是人工编写、AI 编写，还是二者混合，更无法给出比例。** “人主导、AI 辅助开发”是合理的候选解释，但目前不足以把它写成已确认的产品开发事实。

需要分清两种范围：

- **整个当前工作区**：已确认包含本次对话中由 AI 辅助完成的分析/设计文档，以及确定性脚本生成的代码。这可以称为多种来源的混合材料。
- **原项目的应用实现**：人工、AI 辅助和混合编写均可能；现有证据不足以按文件划分，不能由上述文档或生成代码反推全部产品代码的作者。

因此，对“有些人写、有些 AI 写吗”的准确回答是：**文档和工具生成材料有可确认的来源；应用实现是否如此混合、哪些部分由谁编写，当前未知。** Git 提交账户是提交归属，不能证明每一行是该账户的人手输入。

## 2. 为什么代码风格不足以定案

| 可观察现象 | 可能的人工解释 | 可能的 AI 辅助解释 | 判断 |
|---|---|---|---|
| 注释详细，解释历史问题、边界和不变式 | 作者维护复杂系统时记录设计依据 | AI 在任务指令下补充解释和修复注释 | 不具排他性 |
| 大量小 helper、类型和相似分支 | 模块化习惯、lint 限制、重构 | AI 拆分实现或扩展既有模板 | 不能作为 AI 指纹 |
| 命名和语言风格不统一 | 多人、不同阶段、依赖与兼容代码混合 | 多轮生成后人工编辑 | 两种解释均成立 |
| 边界处理复杂、兜底较多 | 长期修复平台/时序问题 | AI 逐次补丁累积 | 必须评估行为，不能反推作者 |
| 功能多但已提交测试少 | 测试未公开、交付方式或覆盖不足 | AI 快速实现后验证不足 | 只支持验证风险评价 |
| 代码里出现 Claude/Codex/Cursor | 产品兼容、插件格式、迁移功能或普通变量名 | 开发者使用相应助手 | 需看具体语义，不能凭关键字定作者 |

例如 [dynamic-workflow-run-replay.ts](../apps/zcode-cli/packages/bootstrap/src/app/dynamic-workflow-run-replay.ts) 的注释详细解释旧词表和冷回放问题。这证明作者/维护者在表达因果关系，但人可以这样写，AI 也可以在源码与任务上下文中这样写。

`Claude/Codex` 在 plugin manifest 兼容和导入历史代码中的出现，属于功能内容；普通 `cursor` 索引变量更不表示 Cursor 编辑器。这些搜索结果不应被计作 AI 署名。

本次不使用风格打分或“AI 检测百分比”。格式化、重构、模板、拷贝、代码生成及人工编辑会让这类推断失去明确的来源含义；本仓库也没有可验证的真值样本支持比例估计。

## 3. 当前能给出的分类

| 材料范围 | 结论 | 证据强度 |
|---|---|---|
| 本次对话编写的分析/设计文档及图规格 | AI 辅助产出，由用户提出任务和本助手执行 | 高：直接过程证据 |
| Archify HTML | 规格驱动的 renderer 产物；规格含 AI 辅助编写 | 高：本次执行过程与产物 |
| Bash command registry | 确定性脚本生成，输入来自第三方数据 | 高：文件头与生成脚本；未在本轮重新生成核对 |
| 生成器脚本本身 | 人/AI 来源未知 | 没有编辑过程记录 |
| Agent Loop、Context、Model、Tool、UI 等产品实现 | 来源未知；人工、AI 辅助、混合均可能 | 缺少可分辨开发轨迹 |
| Git 作者账户 | 可以确定提交归属，不能确定逐行编写方式 | 对 commit 归属强，对代码生成方式弱 |

**不能负责任地声称**“核心是人写、UI 是 AI 写”“大部分由 Claude/Codex 写”或“AI 占 70%”。当前没有支持这些划分的证据。

## 4. 要进一步确认，需要什么

最有价值的是开源前的细粒度 commit/PR、明确 AI 辅助声明、与具体变更对应的编码代理会话/执行记录、原作者对开发方式的说明，以及生成器输入/输出的可复现记录。应取得授权后只查看与目标变更有关的材料，不靠私有账号活动推测作者。

有记录时仍要逐项区分：AI 提建议、人实现；AI 初稿、人修改；AI 自动改代码、人审查；传统生成器输出；以及第三方代码。一个项目可能在不同阶段采取不同方式，不能用单个提交替代整体比例。

本次未访问这些私有资料、未询问原作者、未执行代码生成器，也未建立逐行 provenance。当前报告保留不确定结论，不把“未找到 AI 标记”当成人工证明。

## 5. 对是否采用它作为基座的影响

代码来源可以影响审查方法，但不应成为采用或拒绝的唯一依据。对 ZCode，当前更可验证的决策依据仍是：真实模块边界、状态所有者、工具与业务权限、恢复/幂等、依赖和任务评测。

详细改造结论见 [基座评估](agent-base-assessment.md)。尤其是复杂恢复链缺少提交内回归证据、默认 shell 隔离边界、行业业务副作用保护等问题，应通过源码与测试解决；不能以“像 AI 写的”代替缺陷定位，也不能以“人写的”代替可靠性验收。
