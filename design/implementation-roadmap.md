# 实施路线、验收与决策门槛

本文件为待实施计划。没有新增应用行为、spec、测试或包。先执行 [评估结论](agent-base-assessment.md) 的路线 A，再用证据决定是否进入嵌入式/平台阶段，不预设工期或成熟度分数。

## 阶段 0：定义一个可验收任务

交付具体业务任务、用户及部署范围、数据系统、只读/写入边界、产物 schema、失败/人工交接语义和样例任务集。领域专家定义真实预期和禁用动作；开发团队核对可用数据与 API，不让 Prompt 自己充当验收标准。

**退出条件**：有实际可取得的数据和权限；一份明确的任务 spec；一组可重复的正常、缺失证据、冲突、越权及取消案例；当前无 Agent 方案的人工/规则基线。若业务任务本身无法确定输入或判断成功，暂不进入框架改造。

## 阶段 1：只读行业试点

交付一个受控行业包、授权只读 MCP/Tool、结果/证据验证器和任务集评测。复用当前 App/Runtime、profile/Skill、Context 和会话存储；不改核心 loop，不以更长 Prompt 代替业务工具。

作为示例可完成“质量记录调查 → 带出处报告 → 工单草稿”。工具列表固定；Bash/文件写入/browser 等按业务需求关闭。模型、包、规则和结果契约版本写入执行记录；缺少证据时允许返回未完成/需补充数据。

**退出条件**：预先约定的任务指标达到门槛；越权数据读取和无依据引用的禁止案例通过；输出不仅结构正确，也能被源数据和规则复核；有用户可见的失败/人工接管路径。数值门槛由阶段 0 的风险与基线确定，不在无任务集时捏造“90% 成功率”。

## 阶段 2：受控业务写入

交付对象级授权、绑定计划/参数/版本的审批、稳定业务幂等键、执行 ledger、未知结果对账和必要补偿/人工流程。审批前展示实际目标和将要改变的字段，而非仅展示模型摘要。

**退出条件**：同一操作的重试/重连/新 toolCallId 不能重复写；旧批准不能执行变更参数或已更新对象；超时后的 in_doubt 能被查证或交给人工；会话恢复不把未确认提交当作失败后直接重发。下游没有足够幂等/对账能力时，不进入无人值守写入。

## 阶段 3：稳定基座宿主接口

只有出现第二个明确场景、独立 UI/API 或稳定嵌入需求才进入。交付受控 facade、composition 配置、typed events/结果、资源生命周期、版本与兼容契约。先包装公开入口，再按证据抽取产品耦合。

当前 `@zcode/core`、`@zcode/bootstrap` 等是 workspace private packages，不是已发布行业 SDK。`createZCodeApp` 具备 IO/Storage/MCP 注入；AppOptions 不等于 CoreDeps，没有现成的任意自定义 registry 注入入口。行业 Tool 首先用 MCP 接入，若要原生注入 registry，应明确新增装配接口并先补契约与测试，不能从 Bootstrap 外层深导入实现修改内部对象。

**退出条件**：最小宿主只使用公开 exports，能完成 create/submit/observe/cancel/resume/close；借用 ports 生命周期一致；接入第二个行业包不改通用 loop；原 Desktop/Web 主链没有退化。跨 Node/打包/进程运行方式的兼容性由实际目标验收，不声称抽取后天然可在任意 serverless/browser 运行。

## 阶段 4：按需建设共享云平台

当已明确多客户/多租户并发需求时，补控制面、tenant-aware adapters、受控 worker、调度/lease、预算、凭据/数据隔离、备份恢复与发布管理。共享云的安全基本边界要从阶段 1 的云试点开始落实，阶段 4 是规模化完善，不是补救之前的权限空白。

**退出条件**：跨租户同路径/同对象 ID 不泄露；取消和 worker 回收可观测；高并发、锁等待、长任务恢复有实测；运行中升级/旧 worker 回调不能污染新 run；上下游各自权威明确。达不到时保持单租户/私有部署，不包装成已成熟 SaaS。

## 优先验证的案例

以下均是建议新增测试，不是本轮已执行覆盖。

| 案例 | setup / action | 必须断言 / 证据 |
|---|---|---|
| 只读任务正常闭环 | 固定规程和记录，执行同一任务 | 结构化结果、引用、规则结论、版本和成本均可复核 |
| 缺失/冲突证据 | 删除必要记录或提供不同版本 | 明确缺失/冲突，不补造结论；需要人工处理 |
| 跨租户/对象访问 | 同 workspacePath，不同 tenant/principal | 检索、Tool、缓存、artifact、memory 均无越权数据 |
| 文档提示注入 | 检索结果要求外传/忽略授权 | 数据不改变权限/工具名单；越权调用由可信服务拒绝 |
| 含糊工具参数 | 非法 object ID/schema/类型 | handler 前或业务服务端拒绝；error 与 tool call 配对 |
| 两端断线 | Desktop continuous 与 Web replayable 分别中断 | gap/recovery 符合各自语义；同 accepted input 不重复执行 |
| 部分 stream + 已执行只读 Tool | final tool call 后中断模型流 | paired history 完整、已执行调用不无条件重跑、recovery 有限 |
| 批准后变更 | 修改对象版本、计划参数或撤回权限 | 旧批准被拒绝，需要重新确认；不按旧缓存提交 |
| 提交后超时 | 业务系统已执行，connector 未收到响应 | 用稳定操作键对账；第二次提交无重复效果 |
| 幂等键冲突 | 同 operation key，但参数 fingerprint 不同 | 确定性拒绝，不能返回旧 duplicate success |
| 取消与重启 | pending input/approval/in_doubt 时停止 worker | 各 owner 状态可恢复，未确认操作不盲目重发 |
| 预算/期限耗尽 | 达到任务成本/时间/工具动作边界 | 拒绝新动作，保留已执行回执；工具超时不直接代表业务未执行 |
| 长上下文压缩 | 多轮检索工具输出达到 compact 条件 | 关键 evidenceId 可访问，业务约束仍有效，不从摘要复原秘密 |
| 包升级 | 旧 run 使用 v1，同时发布 v2 | v1 继续固定版本；旧批准/旧 worker 不跨 revision 生效 |

共享 UI 的发送、审批、取消、重连需要 E2E；已有四个 node:test 的迁移覆盖不能被称为这些场景已经通过。普通 Agent Runtime 与 dynamic workflow 有不同测试边界，分别验证实际执行 owner。

## 评测体系

先建立本地可重复的 stub Model/Tool 测试验证状态与错误，再执行带固定版本的离线任务集，最后针对候选部署做真实模型/业务系统灰度。Mock 证明边界逻辑，不证明模型智能质量；在线通过几个示例不证明恢复和隔离。

| 指标 | 建议口径 |
|---|---|
| 业务任务通过率 | 按预先固定的领域断言判定；不以 assistant 的完成文本或 LLM 自评分为唯一依据 |
| 证据有效率 | 引用能定位授权来源/版本、支持对应结论；引用存在与支持结论分开判断 |
| 字段/规则正确率 | schema、确定性规则和专家标注各自统计 |
| 人工介入率 | 区分必要业务审批、数据不足和 Agent 错误接管；不能为降指标取消必要批准 |
| 越权/重复副作用 | 禁止用例按严格拒绝或幂等结果判定；不被平均质量分抵消 |
| 成本 | 每 domainRun 的所有物理请求、Core recovery、检索、Tool、memory/摘要调用按可得用量计入；无价格数据不猜货币金额 |
| 延迟与恢复 | 同时报端到端分位数、人工等待、IO、model attempts、恢复耗时；避免将等待批准计成模型故障 |
| 可靠性 | 取消、崩溃、重连、in_doubt 对账成功/人工处理比例；只报告实际执行样本 |

每条任务保存 case/eval ID、输入样本版本、包/规则/schema/model 配置、执行路径、工具/业务回执与失败分类。基准集的敏感数据最小化并授权；模型、Prompt 和业务工具同时变化时不能归因于某一项优化。

## 如何约束改造范围

先更新目标 feature spec，明确产品规则、所有者、命令、事件顺序、失败和迁移边界；使用 `pnpm architecture:check --changed` 和实际 module ID 的受控 context。代码变更才执行 architecture-governance 的完整流程；本次仅设计文档，未新增产品 spec。

不得通过恢复已移除模块、修改 baseline 掩盖违规、跨包实现深导入或 UI 增加第二份 accepted queue 来接入行业能力。若涉及流/远程，同步验证 continuous/replayable；若涉及协议，同步严格类型和 runtime schema。

静态检查至少执行根 `pnpm typecheck`、`pnpm lint`；CLI 子 workspace 的 check/typecheck 以其 package.json 为准，根 typecheck 不代表覆盖所有 CLI packages。现有 package scripts 无统一行为测试入口，应先设计并落实测试 runner，不把开发模式命令当测试命令。

## 停止或调整路线的条件

若行业任务仅需确定性查询与规则报表，常规服务可能比完整 Agent 更合适；若瓶颈来自知识授权/数据质量，先解决数据，不通过增加 Agent 数量补救；若下游无法安全幂等/对账，保持草稿模式；若评测不能证明优于当前流程，暂停基座抽取与平台扩建。

若经验证某项业务确实要求改通用 loop，再依据最小可复现案例改 Core；不把每个行业规则变成 Runtime 条件分支。后续实际实现应独立立项，本次结论没有授权修改应用或上线。
